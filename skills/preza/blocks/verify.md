# Проверка

Объём — по важности (таблица в SKILL.md). Раунды нумеруй: `render/round<N>/`.

1. Рендер: `scripts/render_pptx.sh <deck.pptx> render/round<N>` — PNG 1280×720 и список встроенных шрифтов (должны быть заявленные). Осмотри каждый слайд.
2. Числа, если есть реестр: `python3 data/check_numbers.py --pptx <deck> --report render/round<N>/numbers.md`, с речью — ещё `--script script.md`. Результат — ноль ошибок.
3. visual-review (обычная и важная) — рубрика ppt-master `references/visual-review.md` по рендеру PowerPoint. Стадию `workflows/stages/visual-review.md` целиком не запускай: она снимает PNG через Playwright из SVG до экспорта, а дефекты экспорта видны только в рендере PowerPoint. Порядок раздачи берётся из неё:
   - записи страниц: N-й PNG раунда — N-я страница `svg_output/` в порядке ppt-master, промежуточные слайды Morph тоже; число PNG и страниц не совпало — остановись. `page_role` — из §IX `design_spec.md`, `canvas` — `viewBox` страницы и размер PNG;
   - пачки по 3 страницы, у колоды больше 30 страниц — по 5: пачки идут параллельно, страницы внутри пачки — по очереди, поэтому время раунда задаёт размер пачки. Все пачки — одним сообщением, модель субагента задана явно (`sonnet`). В задании — абсолютные пути к рубрике, `design_spec.md`, `spec_lock.md` и записи пачки; Style Review Focus, если в проекте есть `templates/design_spec.style.*.md`; по каждому слайду — строка раскадровки и строки отчёта чисел как дополнительный контекст: задача слайда и формулировки при числах;
   - одна итерация: разрешённые рубрикой атомарные правки — в `svg_output/` с копией в `.review/backup/`; остальное и находки по дополнительному контексту — `needs_human` с предложением правки. Отчёты — `.review/<page>.json`, решения по токенам бренда — `.review/brand_review.json`. Субагент возвращает только пути отчётов и сводку до 150 слов;
   - пачки раунда запиши в `PLAN.md` до раздачи и отмечай каждую по возвращении: после паузы или сжатия контекста раздаются только неотмеченные.
4. Сведение — `notes/fixes_round<N>.md` из отчётов `.review/`: применённые правки и `needs_human` — принято, отклонено, почему. `brand_review.json` и другие правки для всей колоды — одним решением: цвет или шрифт — `update_spec.py` ppt-master (до запуска сохрани копию `svg_output/` и `spec_lock.md`: своего отката у скрипта нет), остальное — по всем затронутым страницам.
5. Важная: аудит сводки — ревью Codex (правило в SKILL.md), `plan` — `notes/fixes_round<N>.md` с путями к PNG раунда; после правок — финальная инспекция Codex по последнему рендеру тем же способом, в новой сессии.
5a. **Движение** (в маршруте): рендер показа — итоговые кадры каждого слайда, включая промежуточные; рендер чистой версии — слайдов столько же, сколько страниц без буквы, кадры совпадают с соответствующими слайдами показа. Само движение рендер не видит: пользователь смотрит показ в режиме демонстрации; если доступен PowerPoint под Windows — видео через ppt-master `scripts/powerpoint_video.py`. Экспорт MP4 на Mac анимации объектов не проигрывает (Microsoft) и проверкой не служит.
6. ✅ Спорные правки — пользователю. Принятые правки страниц вносит один субагент (`sonnet`) по `notes/fixes_round<N>.md` целиком — не хост в своём контексте и не субагент на каждую правку; в задании — путь к сводке, `spec_lock.md` и правило ppt-master для вернувшегося проекта (см. [Сборку](build.md), шаг 6). Затем [Сборка](build.md) → новый раунд: его рендер и visual-review проверяют правки. Обычно хватает двух раундов.
7. ✅ Финал: PPTX (и Word речи) в папке проекта, итог в `PLAN.md`.

Готово, когда последний рендер осмотрен целиком, сверка чисел даёт ноль ошибок, серьёзных открытых замечаний нет и пользователь принял финал.
